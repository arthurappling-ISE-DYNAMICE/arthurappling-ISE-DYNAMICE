# Vault Update Protocol (Master)

When adding new knowledge to the vault, follow this sequence:

1. **Identify source.** Where did this come from (a session, a research
   asset, a client engagement, an external tool/trend)?
2. **Determine category.** Which of the vault's numbered folders actually
   fits this piece of knowledge?
3. **Extract useful principles.** Pull out the durable pattern or lesson —
   don't archive raw material wholesale.
4. **Reject hype.** If it's impressive-sounding but unproven, it is not
   ready for the vault yet (see `12_Research_Archive/RESEARCH_ASSET_RULES.md`).
5. **Record implementation timing.** Note whether this is for now, later,
   or never.
6. **Add to Future Features Shelf if not now.** Use
   `06_Future_Features_Shelf/FUTURE_FEATURES_BACKLOG.md` with a clear
   revisit condition.
7. **Add a decision if it changes architecture.** Use
   `03_Engineering_Decisions/DECISION_LOG_TEMPLATE.md`.
8. **Add a lesson if it came from failure/recovery.** Use
   `04_Lessons_Learned/`.
9. **Add a session log after major work.** Use
   `13_AI_Session_Logs/AI_SESSION_LOG_TEMPLATE.md`.
10. **Never store secrets.** No passwords, API keys, tokens, or private
    credentials in any vault file, ever.

This protocol governs *all* additions to the vault — it sits above the
individual per-folder rules and the `AI_UPDATE_PROTOCOL.md` intake
checklist in this same folder.
